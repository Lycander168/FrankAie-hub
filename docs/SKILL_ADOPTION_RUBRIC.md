# Skill 安裝前評估標準（Skill Adoption Rubric v1.0）

> 用途：任何外部 skill / plugin 要進入 FrankAie-hub 之前，一律先跑這套評估。
> 目的不是擋，是避免「裝了但用不到」與「裝了打壞既有結構」兩種常見失敗。
>
> 適用對象：外部 skill、plugin、MCP server、或任何需要新增執行期依賴的工具。
> 不適用：純內部新增角色 persona skill（走 `plugins/frankaie-research-hub/README.md` 的新增流程即可）。

---

## 評估流程

1. **事實蒐集** — 實際取得該 skill 的原始碼／文件，確認它「真的做什麼」，不採信行銷描述。
2. **專家交叉驗證** — 至少 3 位獨立評估者，彼此不共享結論，各自獨立打分：
   - **架構稽核**：與現有 skill 的功能重疊、觸發詞衝突、CI／慣例相容性
   - **技術可行性**：在實際執行環境中**實測**安裝與產出，不接受「理論上可行」
   - **商業價值**：需求強度、替代方案、使用門檻、投入產出比
3. **加權計分** — 依下表六構面計分，取各評估者同構面平均後加權。
4. **依門檻決策** — 見「決策門檻」一節。

> 規則：技術可行性構面**必須有實測證據**（安裝紀錄、產出檔案、錯誤訊息）。
> 無實測者該構面一律以 3 分計，並在報告中標註「未實測」。

---

## 六大評分構面與權重

| # | 構面 | 權重 | 衡量什麼 |
|---|------|------|----------|
| D1 | 需求必要性與使用頻率 | 25% | 真的缺這個能力嗎？裝了會被用幾次？ |
| D2 | 非重複性／能力加值 | 20% | 和現有能力是互補還是重工？ |
| D3 | 技術可行性 | 15% | 在我們的環境裡跑得起來嗎？（需實測） |
| D4 | 衝突與誤觸風險 | 15% | 會不會搶觸發、誤觸後會不會造成副作用？ |
| D5 | 整合與維運成本 | 15% | 導入要改幾個檔？之後誰維護？ |
| D6 | 授權與合規 | 10% | 商用授權、費用、資料外流風險 |

> D4、D5、D6 為**逆向構面**：分數越高代表風險／成本越低。

---

## 1–5 分級錨點

### D1 需求必要性與使用頻率（25%）

| 分數 | 定義 |
|------|------|
| 5 | 補上一個**現在正在阻塞業務**的缺口；可預期每週使用 |
| 4 | 補上明確缺口，每月固定使用場景 ≥ 2 個 |
| 3 | 缺口存在但可繞道；每季用得到 |
| 2 | 有想像中的用途，但現有流程沒被卡住；一年數次 |
| 1 | 想不出具體要在哪個既有流程中使用 |

### D2 非重複性／能力加值（20%）

| 分數 | 定義 |
|------|------|
| 5 | 現有 skill 與可用 MCP 完全沒有對應能力，且明顯延伸既有 SOP 的下一段 |
| 4 | 主體能力不重複，僅少數邊緣功能與既有 skill 同層 |
| 3 | 約一半能力已被現有工具覆蓋，加值集中在特定場景 |
| 2 | 多數能力現有工具已能達成，只是做法不同 |
| 1 | 功能與既有 skill 高度重疊，屬重工 |

### D3 技術可行性（15%）

| 分數 | 定義 |
|------|------|
| 5 | 已在本環境**實測完成端到端產出**，效能可接受 |
| 4 | 實測可跑，但需要少量已驗證的設定調整 |
| 3 | 未實測，或實測部分成功、關鍵環節待驗證 |
| 2 | 實測受阻，需額外基礎設施（系統套件、外部服務、額度） |
| 1 | 在本環境無法運作 |

### D4 衝突與誤觸風險（15%，分數越高風險越低）

| 分數 | 定義 |
|------|------|
| 5 | 觸發詞完全不重疊，誤觸也只是多產一段文字，無副作用 |
| 4 | 少數觸發詞相近，但有明確判別詞；誤觸無副作用 |
| 3 | 有可預期的雙觸發情境，且**誤觸會產生副作用**（執行指令、寫檔、起 server） |
| 2 | 觸發詞大量重疊，且既有路由（`hub-router`）無仲裁規則可循 |
| 1 | 會穩定搶走既有 skill 的觸發，或誤觸會造成破壞性操作 |

### D5 整合與維運成本（15%，分數越高成本越低）

| 分數 | 定義 |
|------|------|
| 5 | 一行安裝，CI 全綠，零檔案需同步 |
| 4 | 需更新 1–2 個文件（ROSTER／README），CI 全綠 |
| 3 | 需更新 3–5 個檔案，或需一次性 ≤ 1 天的封裝工程 |
| 2 | 會使 CI 失敗，需修改檢查腳本或上游檔案；或需 1–2 天封裝並持續維護 |
| 1 | 需重構既有慣例（Pattern／CI／目錄結構）才能容納 |

### D6 授權與合規（10%，分數越高風險越低）

| 分數 | 定義 |
|------|------|
| 5 | 寬鬆開源授權（MIT／Apache），商用無條件免費 |
| 4 | 開源授權，商用免費但有註明義務 |
| 3 | 免費額度充足，超量才付費，且門檻遠高於我們的規模 |
| 2 | source-available／商用需付費，且**我們的規模很可能落入付費區間** |
| 1 | 授權禁止我們的使用方式，或有資料外流／合規疑慮 |

## 決策門檻

| 加權總分 | 決策 |
|----------|------|
| **≥ 4.50** | **自動安裝**，並同步更新 ROSTER／README／`hub-router` 路由表 |
| 3.50 – 4.49 | **條件式安裝** — 先補齊報告列出的前置條件，補齊後複評 |
| 2.50 – 3.49 | **暫緩** — 記錄於待辦，先用替代方案；觸發條件成立時重評 |
| < 2.50 | **否決** — 寫明否決理由，避免日後重複討論 |

### 一票否決條款（不論總分）

1. 任一構面得 **1 分** → 直接否決，除非該項有已驗證的緩解方案。
2. **D6 ≤ 2** → 不得自動安裝，需先取得授權／預算簽核。
3. 導入後會使 **CI 由綠轉紅** → 不得自動安裝，必須先確定不破壞 CI 的安裝路徑。
4. 三位評估者同一構面分差 **≥ 3 分** → 視為證據不足，補做實測後重評。

## 報告格式

每次評估產出一份 `docs/skill-assessments/YYYY-MM-DD-<skill-name>.md`，至少包含：

1. 事實基準（版本、來源、實際內容）
2. 各評估者獨立分數表（不合併，保留分歧）
3. 加權計分表與總分
4. 決策與理由
5. 若為條件式安裝／暫緩：**明列前置條件與重評觸發點**
